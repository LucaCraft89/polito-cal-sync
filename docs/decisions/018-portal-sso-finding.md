# 018 Finding: the portal SSO login works unattended with a password (owner run, 2026-11-04)

**Observed** (probe 05, third owner run, fresh cookie jar, no browser state):

- 13 requests, all to `didattica.polito.it` and `idp.polito.it`: portal `/login` -> `/secure/login` -> IdP SSO redirect -> IdP login form -> **one password POST (200, SAML response form)** -> POST to `/Shibboleth.sso/SAML2/POST` (302) -> a chain of portal redirects -> `GET /pls/static/studente/` (200) -> `GET /pls/portal30/sviluppo.studente.getStudentData` (200, JSON).
- **No MFA step and no extra form** for this account from a headless client. (Open caveat: the owner has a passkey registered. The IdP may ask for MFA from other networks or after changes; this was one run.)
- **IdP cookies:** `__Host-shib_idp_session` and `__Host-shib_idp_username` with `Max-Age=7776000` (90 days). Portal cookies (`owa_session`, `dida_portal`, `_shibsession_*`, `ShibCookie`, ...) are **session cookies**: the server-side lifetime of the portal session is not stated and was not measured.
- `getStudentData` is one JSON document with sections `orari` (lectures: `id, courseId, startsAt, endsAt, type, description, courseName, url, place{name,siteId,buildingId,floorId,roomId}, virtualClassrooms`), `appelli` (exam calls: `id, idBooking, courseShortcode, courseName, type, classrooms, notes, bookingStartsAt, bookingEndsAt, examStartsAt, examEndsAt, startDate, endDate, url`), `agenda` (`name, date, ISOdate, type, id, startDate, endDate, title, agendaGroup`), `carico` (courses: `id, name, shortcode, cfu, teacherName, year, ...`), `textExercise.exams`, `virtualClassroom`, `materialeRecente`, `career`, `anagrafica` and others. **Key names are known; date formats and values are not** (the sanitized sample has not been shared yet). `startsAt/endsAt` have 25 characters (looks like an ISO date-time with an offset); `examStartsAt`, `bookingEndsAt` have 19 (no zone: probably local time, UNVERIFIED); `bookingStartsAt` is an empty string when unset.

**Correction to decision 017.** The run that failed with the login form redisplayed sent the **same field names** as the successful one. The `_eventId_proceed=1` theory is therefore **not what fixed it**; the refused run was most likely a credentials typing issue (the username/password lengths typed differ between runs). The code still sends `1` when the field is empty, as the browser's script does; it is harmless but unproven to be needed.

**Decided**

- **Route B is the Polito source.** The app API skeleton (`fields.ts`, `schemas.ts`, `map.ts`, `client.ts`, decision 015) is based on guesses that were never confirmed and a login that could not be called; it is to be **replaced** by a portal adapter after the sanitized sample is in. Until then it stays disabled and untouched.
- **Login client done** (`src/sources/polito/portal/`): the verified flow, one request at a time (1.5 s apart), allow-listed hosts and https only, the password POSTed once and only to a login form on an allowed host, the SAML answer forwarded only to an allowed host, no retries inside a login, 429 and 5xx are fetch failures, a redisplayed login form is `E_POLITO_API_AUTH_REJECTED`, any other IdP form is `E_POLITO_LOGIN_EXTRA_STEP` and is not answered. Tested with a fake IdP.
- **Lockout protection:** after a refused login, `LoginLatch` (`DATA_DIR/polito-login-blocked.json`, a fingerprint of username+password) pauses all attempts until the credentials change (`E_POLITO_LOGIN_BLOCKED`). An hourly retry of a wrong password must never happen.
- **Credentials:** to be read from `POLITO_USERNAME` and `POLITO_PASSWORD` in `.env` (git-ignored, placeholders in `.env.example`, redacted from logs), like the Google client secret. Not wired in yet.
- **Not yet decided:** reusing the 90-day IdP session cookie between runs (fewer password logins; but it is a long-lived credential on disk in `DATA_DIR`, 0600). Cost today: a full login (13 requests) plus one data request per sync interval.
- **Remains true:** the source is disabled by default, fails closed (`complete: false` on any mismatch, no deletions), and never touches ICS events.
- **Risk to state in the README when it ships:** this logs in with the student's password the way a browser does; it is not an advertised API, it may break when the portal changes, and a new "device" can trigger MFA at any time (then the source stops with `E_POLITO_LOGIN_EXTRA_STEP`).
