# 023 Settings store and secured web API (first step of M5, built early)

**Context.** PLAN open decisions 4 and 5. The owner did not object to building `docs/UI.md` section 8 step 1 early. Built: settings store, secured JSON API, auth/session/CSRF/headers, security tests. **No pages.** Off by default (`UI_ENABLED=false`).

**Decided**

- **HTTP server: extend `node:http` (decision 012), do not add `fastify`.** The API is 8 routes returning JSON; validation is `zod`, which we already use; the Host check, status endpoints and tests already exist on `node:http`. A framework would add a dependency (plus cookie/helmet-style plugins) to a security-sensitive local tool for little gain, and every header is set by our own code and tested. AGENTS.md lists fastify in the stack; this is a deliberate deviation, and it is cheap to reverse because handlers are plain `(req, res)` functions in `src/web/app.ts`. Revisit if pages need streaming or many routes.
- **Settings model.** `DATA_DIR/settings.json` (version 1, mode 0600, atomic write) holds flat dotted keys (`polito.password`, `icsUrls`, ...) from ONE table, `src/settings/fields.ts`: UI key, env variable, shape, how it becomes env text, how it is shown. `loadConfig(env, settings)` turns the file into env text and lets every non-empty real variable win, so there is a single validation path (the old `envSchema`), `.env` and the UI mix freely, and the CLI uses `loadConfigFromDisk`. A variable that is set locks its setting: shown as `source: env`, changes refused (`E_SETTING_LOCKED`). Env-only on purpose: `DATA_DIR`, `LOG_LEVEL`, `STATUS_*`, `UI_*` (a page must not move the data folder or widen who can reach it).
- **Writes are all-or-nothing and checked against the `.env` rules** (`E_SETTING_INVALID` names key and rule, never the value). A damaged or newer file is `E_SETTINGS_FILE_INVALID`, never ignored.
- **Secrets.** `polito.password` and `google.clientSecret` are write-only (the API says `set: true` and nothing else; clearing is `clear: [key]`). **Feed URLs are treated as secrets too** (they embed tokens): the view shows `{index, host}` only. Stored in clear text in the 0600 file, like `.env`; no key beside them (UI.md section 4). The audit log (`audit.log`, 0600) records which keys changed and never values.
- **Auth.** Passphrase: min 12 characters, max 256, at least 5 distinct, no composition rules; scrypt (N=2^15, r=8, p=1, 16-byte salt) in `ui-auth.json`. Sessions: random 256-bit id kept only as a hash, in memory, idle 30 min, absolute 12 h, at most 50, all dropped on passphrase change. Throttle: 2 free typos per address, then 2 s doubling up to 15 min; 30 failures from anywhere in 15 min block everyone; while blocked even the right passphrase is not checked. `reset-ui-passphrase` (CLI) is the recovery.
- **Request pipeline** (`src/web/app.ts`): Host allow-list (421) -> route (404/405) -> `Origin` must equal `<scheme>://<Host>` and `Sec-Fetch-Site` must be same-origin, on every non-GET including login and setup -> session (401) -> CSRF header, timing-safe (non-GET) -> JSON body (type, 256 KB, object, strict fields). Early errors close the connection (found by a test: a keep-alive client hung after a rejected oversized body). All answers carry the headers of UI.md section 4; no CORS.
- **Deviations from UI.md, with reasons.**
  1. "Refuses to start on a non-loopback bind without HTTPS" is replaced by: the Host allow-list defaults to the loopback names, extra names need `UI_ALLOWED_HOSTS`, and `UI_HTTPS=true` marks a TLS proxy (Secure cookie, https Origin, HSTS). The Docker image binds 0.0.0.0 inside the container while compose publishes on the host's 127.0.0.1 (decision 012), so a bind-address rule would break the default setup.
  2. "First run only from loopback" is implemented as "only with a loopback **Host** header": inside Docker the peer address is the bridge gateway, never loopback.
  3. `X-Forwarded-For` is not trusted, so behind a proxy all logins share one address and the throttle acts as the global one.
- **Serve picks up changes.** `serve` reloads `settings.json` + env before every run (sources, login, squads, exam calls apply from the next run); the interval, status port and UI switches need a restart. A settings file that became invalid keeps the previous settings and logs a warning.

**Not built (next steps of M5):** any page; preview/sync endpoints with the 15-minute rate limit and single flight; Google connect and "Test" buttons; the stored-XSS rendering test (nothing renders text yet; answers are JSON with `nosniff` and a no-script CSP); `doctor`. In-memory sessions and throttle counters are lost on restart (acceptable: login again).

**Tests:** `test/settings.test.ts`, `test/web-api.test.ts` (22 cases for UI.md section 7.4: CSRF, Origin, Host incl. no Host header, headers on every answer, expiry, throttle, secrets absent from answers/logs/audit, 0600, env lock, GET changes nothing, body limits), `test/web-cli.test.ts` (settings reach the CLI, `reset-ui-passphrase`, `serve` mounts the API only when enabled). All against the real HTTP server on an ephemeral port with fakes; no real account involved.
