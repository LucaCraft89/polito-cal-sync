# 036 The live Moodle source

**Decided** (`src/sources/moodle/`, setting `moodle.enabled` / `SOURCE_MOODLE_ENABLED`, off by default)

- **Why a source and not the export link.** Owner wants Moodle "live synced like the Polito one". Evidence: decisions 033 to 035. The link export is fresh on every request (measured: `DTSTAMP` and `Last-Modified` = request time, no ETag, a conditional GET answers 200), but its window is fixed by `preset_time` (`recentupcoming` and `monthnow` stop after about 15 days, `custom` reaches a year, nothing before the first of the current month). The web service has the past, the course of each event and needs no link.
- **Login.** The Moodle app's flow through the university SSO, headless, with the same login client as the portal (`PortalSession` gained `captureScheme`: a redirect to `moodlemobile://token=...` ends the login and is never requested). Verified live by the owner's probes (no MFA, 15 requests), **not** by the program: the program's own run against the real Moodle has not been done. **Same account, same latch** (decision 018): a refusal at either place pauses both; MFA/extra step stops the source, nothing is latched.
- **Token.** Kept in `DATA_DIR/moodle-token.json` (0600), bound to a hash of the username, used until Moodle answers `invalidtoken`, then ONE new login and ONE retry (a token refused right after a fresh login is an error, not a loop). Sent in the POST body only, never in an address, log or error. **Lifetime unknown**; the design does not depend on it. The private token of the redirect is dropped.
- **Calls** (one pass = three requests, 1 s apart): `core_webservice_get_site_info` (user id), `core_enrol_get_users_courses` (names), `core_calendar_get_calendar_events` for 366 days back and ahead with the user's courses, user and site events, hidden ones skipped. This is the call that probe 08 showed returns exactly what the month view shows (31 of 31); the action-event and upcoming calls are not complete and are not used.
- **Mapping.** Kind `moodle`, title `[Moodle] <name>`, start = `timestart`, end = start + `timeduration` (0 = a point in time), description = "Course: <name>" plus the description with HTML reduced to text, link = the course page, course key `moodle:<course id>`, source `moodle`, id = Moodle's event id. Times are Unix seconds, so no time-zone guessing. The page and the Overview show course names through the same course-name map as the portal.
- **Fail closed** as decision 019: `complete: true` only if all three calls answered and every event was understood (positions and field names only in the problem). A Moodle exception, a missing list, an outage, a refused login: nothing written for this source and nothing deleted for it, and the other sources are unaffected. It never throws.
- **Duplicates.** The ICS feed from Moodle has source `ics` and the UID as id; this has source `moodle` and the event id. Both on = every event twice. The UI card and SETUP.md say: remove the Moodle feed when switching on. Switching deletes the feed's Moodle events (the feed source returns them no more) within the deletion limit.
- **Test button** `POST /api/sources/moodle/test`: counts only; once per 15 minutes per set of credentials; a paused login answers with no request; uses the saved token (so usually no login). `doctor` has the same check (a paused login makes no request, `--local` contacts nobody). New code `E_MOODLE_API_ERROR`.
- **Not done:** assignments (the one account has none; `mod_assign_get_assignments` is known to answer but unmapped), per-course calendars, a deadline/other-kind distinction (all are kind `moodle` as in decision 020), multi-day events are one event from start to end.

**Verified how.** `test/moodle-source.test.ts` (16 cases + one end-to-end through `runConfiguredSync` with the in-memory calendar: create, no-op second run, patch and delete, an outage deletes nothing) and `test/web-moodle.test.ts` (5), against an invented Moodle behind the invented IdP (`test/support/moodle-world.ts`): mapping, window parameters, token reuse without a login, token in the body only, a reset token, no retry loop, the shared latch, an extra step, exceptions, a missing list, a malformed event keeping the rest, outage, a foreign host. **Not run live from here** (the live-test rules cover only the portal hosts).
