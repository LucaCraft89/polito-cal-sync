# 027 Connect Google and choose the calendar from the UI

**Decided**

- **Same flow as `auth google` (decision 011), driven by the server.** `POST /api/google/connect` starts `loopbackAuthorize` in the background (PKCE, `state`, 5 minute limit) and answers with the Google address to open and the local port Google sends the browser back to; the page shows a link (only `http(s)` is ever linked, `rel=noopener`) and polls `GET /api/google` every 2 s. One sign-in at a time: a second start joins the waiting one. `POST /api/google/connect/cancel` ends it and frees the port. A port that is taken is answered at once (`E_GOOGLE_AUTH_FAILED`), not left waiting. Added to `loopbackAuthorize`: an abort signal, the redirect address in `announce`, and the browser tab says "go back to the program" instead of "the terminal".
- **Docker:** the UI flow listens on `GOOGLE_AUTH_BIND` / `GOOGLE_AUTH_PORT` (env only, default `127.0.0.1` and any free port). The image sets `0.0.0.0` and `8789`; compose publishes `127.0.0.1:8789`. **Not run in Docker** (no Docker run in the build session).
- **Status** `GET /api/google`: client saved, connected (a login file exists; it may still have expired, a sync says so), account, calendar name, whether `GOOGLE_CALENDAR_ID` locks the choice, a damaged login file as a three-line problem, and the state of the sign-in. No network call, no token, no client secret. The account is the id of the main calendar (= its email address), read once after sign-in and kept in `google-account.json` (0600). **A sign-in with another account than before clears the saved calendar** (it belongs to the other account). Same account keeps it. The calendar name is kept next to the id in `google-calendar.json` for display only.
- **Picker** `GET /api/google/calendars` lists calendars the owner can edit, **never the main calendar**, never read-only ones, at most 100, plus how many were hidden. `POST /api/google/calendar` takes `{id}` or `{create:{name?}}` and goes through the existing `chooseCalendar`/`assertDedicatedCalendar`, so the main calendar (its id or `primary`) is refused with `E_GOOGLE_CALENDAR_IS_PRIMARY` and a read-only one with `E_GOOGLE_PERMISSION_DENIED`. `create` reuses an owned calendar of the same name, otherwise creates it. Never deletes a calendar. Locked by `GOOGLE_CALENDAR_ID` (`E_SETTING_LOCKED`); a calendar id saved as a setting is cleared by a new choice so the choice wins. Calendar names are Google's text and are shown as text.
- **HTTP statuses** for Google errors are never 401 (the page reads 401 as "session ended"): 409 client missing / login expired, 400 sign-in failed, 422 main calendar, 403 no permission, 404 calendar gone, 429 quota, 502 Google down.
- **Overview** now has three Google steps: client saved, account connected, calendar chosen. The "auth google" notes are gone from Overview and Settings.

**Verified how.** `test/web-google.test.ts` (18 cases, real HTTP server, a fake OAuth client of the real interface, an in-memory calendar list, the browser simulated by a request to the loopback address) and a Playwright test (save client, connect, link, auto-detect, pick with a hostile calendar name, create, Overview) with layout and axe checks in each state. The browser test found a real bug (the connect button posted without a JSON body and was refused); fixed. **Nothing was run against real Google**: no real consent page, token exchange, calendar list or insert. What stays UNVERIFIED: that Google's primary calendar id is the account's email (the code only needs `primary: true`; the id is display), and the whole real consent flow with this redirect (same code as the CLI, which the owner has not run either).
