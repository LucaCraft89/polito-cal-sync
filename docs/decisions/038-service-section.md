# 038 The Service section: the scheduled sync under the owner's control

**Context.** The owner: the program runs in Docker and must keep the calendars synced on its own "every x hours", and the UI had no section for it. Before this, `serve` synced every `SYNC_INTERVAL_MINUTES` and the page only showed a status line; the interval was in Settings and needed a restart.

**Decided**

- **A Service page** (the old History page, renamed, nav label "Service"; `#/history` still works): status (on and waiting, syncing now, paused, needs attention) with last run, last success, next run, counts and the last problem in the three-line form; a **Schedule** card (switch "Keep my calendar up to date automatically" and **Sync every (hours)**, 0.25 to 24, stored as minutes, 15 to 1440 as before); the run history; the paused-login state. The Overview "Automatic sync" card shows the same state and links to it. The interval field left Settings.
- **New setting `syncAuto`** (`SYNC_AUTO`, default **true**, so existing setups behave as before; an environment variable locks it like any setting). Off = the loop idles, no run, and the heartbeat says `autoSync: false`, which `evaluateHealth` treats as healthy (paused on purpose is not a fault, so the Docker healthcheck does not restart the container).
- **The loop re-plans at once** (`ServeLoop`): `intervalMinutes` may be a function and `enabled` a function, both read before every wait; `poke()` wakes the wait. The web app calls `settingsChanged()` after every successful settings save (`serve` re-reads `settings.json` + env, then pokes). The next run is `end of the last run + the NEW interval`: a shorter interval can make a run due immediately, a longer one postpones it; switching on after being off runs at once, switching off never interrupts a run in progress. Waits are cut into slices of at most 5 minutes (a changed system clock cannot strand it). The first run still happens when the service starts (if switched on). Heartbeat gained `autoSync` and `running`. All of this is tested with real timers (`test/m2-flow.test.ts`).
- **Safety unchanged:** a scheduled run never forces (decision 001); beyond the limit it is refused and waits for the owner (Preview, Sync now with the typed phrase). The Service page says so. A scheduled run and Sync now share the run lock (decision 012): pressing Sync now during a scheduled run gives `E_SYNC_ALREADY_RUNNING` ("wait a minute"), as seen by the owner; the page now also learns of the run through the live updates.
- **Docker:** the container already runs `serve` with `restart: unless-stopped`; nothing new is needed there. `.env.example` documents `SYNC_AUTO`.
- **Not done:** several schedules, a time-of-day window ("only at night"), a "run a scheduled-style sync now" button (Sync now covers it, with its preview rule).

**Verified how.** Loop tests (idle while off, run on switching on, heartbeat flags, a changed interval applies at once in both directions, health while paused), `test/web-live.test.ts` (service view, settings tell the loop only when saved, locked by env, a run that changed the calendar invalidates the preview) and a Playwright test on a phone (layout and axe, the page follows running/paused, the schedule is saved in hours and stored as minutes, an invalid value shows the three-line error).
