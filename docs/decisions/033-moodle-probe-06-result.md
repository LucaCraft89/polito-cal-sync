# 033 Moodle probe 06 result: a headless SSO token works

**Observed** (owner run, 2026-11-05, `probe/out/06-moodle-token.json`, 15 requests).

- The app login flow works headlessly with the same IdP form as the portal: `launch.php` -> Moodle login -> Shibboleth SP -> `idp.polito.it` form (one password POST) -> SAML POST back -> `launch.php` 302 -> a token (32 characters, plus a private token). **No MFA and no extra step.** The IdP cookies are the 90-day ones seen in decision 018. Whether the Moodle token expires, and when, is **not known** (one run).
- Moodle 4.5.13+ (`2024100713.01`); the mobile service allows 441 functions, among them `core_calendar_get_calendar_events`, `..._monthly_view`, `..._action_events_by_timesort`, `..._export_token`, `core_enrol_get_users_courses`, `mod_assign_get_assignments`. All calls answered 200.
- `core_enrol_get_users_courses`: 5 courses (ids, short and full names). `mod_assign_get_assignments`: 0 assignments (these courses have none, so no due dates came from there).
- `core_calendar_get_action_events_by_timesort` (30 days back to 120 ahead): only **3 events, all quiz "open"** events. That function returns only events that carry an action, so it is **not** a full calendar. `core_calendar_get_calendar_upcoming_view` returned 10 events with other modules and types but is capped (the user's calendar preferences: lookahead and max events), so it is not complete either.
- Event fields (names): `id, name, description, location, modulename, eventtype, component, instance, timestart, timeduration, timesort, course{id, fullname, shortname}, url, viewurl, formattedtime, ...`; times are integers (Unix seconds), zero `timeduration` is a point in time.
- `core_calendar_get_calendar_export_token` returns the 40-character export token: the export link can be rebuilt by the program at any time (no manual copy, no stale link).

**What this settles and what it does not.** The way in exists and needs no MFA. Which function returns the **complete** calendar (the one the export link lacks events from) is not settled by this run: the two functions used are action-only and capped. The candidates are `core_calendar_get_calendar_events` (the legacy window query the export itself uses) and the monthly view. `probe/07-moodle-events.mjs` asks the first for the whole window, downloads the export in three time-period variants, and compares by event id, printing only counts by event type, module and month. That is the evidence that says what the export misses and why (time window, event types, hidden events).

**Decided.** No source is written yet (the answer shape of the complete query has not been seen). After probe 07: build `src/sources/moodle/` on `core_calendar_get_calendar_events` (or whichever the comparison shows complete), token fetched by the SSO client extended to `moodle.polito.it`, stored like the Polito login in `DATA_DIR` (0600), fail-closed like decision 019, kind `moodle`, course key from the event's course id; keep the export feed as the credential-free fallback. The 90-day IdP cookie and the token lifetime decide how often a full login is needed (open).
